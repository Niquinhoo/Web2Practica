Pruebas automatizadas e integración continua

Imaginá que alguien modifica ListaServiceImpl y, sin darse cuenta, elimina la comprobación de propiedad. El proyecto sigue compilando y ningún endpoint falla, pero ahora cualquier usuario puede leer las listas de otra persona. Una prueba automatizada convierte una regla del negocio en una comprobación repetible, y la integración continua la ejecuta ante cada cambio, antes de que el error llegue a producción.

En este apunte veremos:

  • qué comprueba una prueba unitaria y qué una de integración;
  • cómo se escriben en el TP3, con Mockito, MockMvc y Testcontainers;
  • cómo Maven descubre y ejecuta cada tipo de prueba;
  • qué verifica la integración continua y cómo leer su resultado, con GitHub Actions como ejemplo.

1. Qué problema resuelven las pruebas

Sección titulada «1. Qué problema resuelven las pruebas»

Un cambio puede romper algo lejano a donde se hizo. Las pruebas automatizadas dan una respuesta rápida a una pregunta: ¿el sistema sigue haciendo lo que prometía?

Una buena prueba verifica un comportamiento observable, no los detalles internos de la implementación:

  • falla si el comportamiento se rompe;
  • sigue pasando si la implementación cambia pero el comportamiento se conserva.

También importan los casos negativos. En seguridad, comprobar que una solicitud ajena se rechaza es tan importante como comprobar que la propia se acepta. Una API que solo se probó con el camino feliz puede estar abierta sin que nadie lo note.

2. Tipos de pruebas

Sección titulada «2. Tipos de pruebas»
Unitaria De integración De contrato
Qué comprueba Una regla o clase aislada Varias piezas trabajando juntas con tecnología real Que la forma de una interacción coincida con lo acordado
Dependencias Simuladas o en memoria Reales: el contexto de Spring, la seguridad y la base de datos Del lado del consumidor o del proveedor
Velocidad Milisegundos Segundos: levanta el contexto y la base Depende de la herramienta
Falla cuando Cambia la regla de esa clase Dos piezas no encajan: una migración, un filtro, un mapeo Cambia el contrato publicado
En el TP3 UsuarioServiceImplTest ListaControllerIT Solo como comparación

Conviene tener muchas pruebas unitarias, rápidas, y menos pruebas de integración, más lentas, que cubran las uniones entre piezas. Las de contrato comprueban que una API o un cliente respeten un acuerdo; en este curso solo las comparamos.

Una prueba unitaria no necesita Mockito por definición, ni una de integración necesita arrancar toda la aplicación. Son herramientas para resolver un problema: aislar o integrar lo que se quiere comprobar.

3. Prueba unitaria: la regla sin infraestructura

Sección titulada «3. Prueba unitaria: la regla sin infraestructura»

Una prueba unitaria comprueba la lógica de una clase reemplazando sus colaboradores. Se organiza en tres pasos: preparación, acción y verificación.

Los reemplazos de colaboradores se llaman dobles de prueba:

Doble Qué hace Ejemplo
Stub Devuelve respuestas fijas. existsByEmail siempre devuelve false.
Mock Registra cómo lo usaron para poder verificarlo. Comprobar que se llamó a save.
Fake Implementación simplificada pero funcional. Un repository en memoria, como el del TP1.

El Service del TP depende de la interfaz UsuarioRepository, un puerto, y no de JPA. Por eso se puede probar sin base de datos, como vimos en Arquitectura y dominio.

  • @Mock reemplaza al repository por un doble que no toca ninguna base.
  • El PasswordEncoder es el real, a propósito: el hash es justamente lo que se quiere probar y no conviene simularlo.
  • ArgumentCaptor recupera el Usuario que el Service quiso guardar para inspeccionarlo.
  • La verificación es doble: el hash es distinto del texto plano y corresponde a esa contraseña. Con solo la primera, un hash cualquiera pasaría la prueba.
  • El nombre del método sigue la convención que se explica a continuación.

Cómo nombramos las pruebas

Sección titulada «Cómo nombramos las pruebas»

Una convención de nombres hace que las pruebas se encuentren, se ejecuten con la herramienta correcta y se lean como una especificación. En el TP3 usamos esta:

Qué se nombra Convención Ejemplo
Clase unitaria <ClaseProbada>Test ListaServiceImplTest
Clase de integración <Recurso>IT ListaControllerIT
Paquete El mismo que la clase probada, bajo src/test/java service con service
Método operación_escenario_resultado obtener_listaAjena_lanzaAccesoDenegado
  • El sufijo de la clase no es cosmético: decide quién la ejecuta. Surefire, con ./mvnw test, reconoce *Test; Failsafe, con ./mvnw verify, reconoce *IT. Una prueba unitaria llamada ListaServiceImplIT no correría con test. La sección 5 de este apunte lo desarrolla.
  • La clase lleva el nombre de lo que prueba: ListaServiceImpl tiene su ListaServiceImplTest, en el mismo paquete pero bajo src/test/java. Se encuentra con el buscador del IDE y se nota enseguida qué clase no tiene pruebas.
  • El método se escribe en tres partes separadas por guion bajo, cada una en camelCase, y se lee como una frase: obtener, lista ajena, lanza acceso denegado. La operación es lo que se invoca (obtener, login, validar). El escenario es la condición (listaAjena, tokenVencido, conCredencialesInvalidas). El resultado es lo observable (devuelve403, lanzaAccesoDenegado, noEscribeNada).
  • Si el escenario es evidente o no hay una operación clara, se omite esa parte, como en conTokenInvalido_noAutenticaYContinuaLaCadena o accederAListaAjena_devuelve403, pero el nombre termina siempre con el resultado esperado.
  • Importa porque Maven imprime ese nombre cuando una prueba falla. Un nombre como test1 obliga a abrir el código; validar_tokenVencido_lanzaExcepcion ya dice qué regla se rompió.

4. Prueba de integración: las piezas juntas

Sección titulada «4. Prueba de integración: las piezas juntas»

Todas las pruebas unitarias pueden pasar y la aplicación igual fallar: una migración que falta, un filtro de seguridad mal ubicado o un mapeo que no coincide con la tabla no se ven con dobles. Una prueba de integración usa componentes reales en la frontera que quiere comprobar.

En el TP3 se combinan tres herramientas:

Herramienta Qué aporta
@SpringBootTest Levanta el contexto completo de la aplicación.
MockMvc Envía solicitudes HTTP simuladas, sin abrir un puerto, y ejecuta la cadena de filtros de seguridad.
Testcontainers Arranca un PostgreSQL real dentro de un contenedor Docker descartable.

Usar la misma base que en producción, y no una base en memoria con otro motor, evita diferencias de comportamiento en restricciones, tipos o SQL. Además, Flyway aplica las migraciones V1 a V6 sobre una base limpia en cada ejecución, de modo que la prueba también verifica que el historial de migraciones funciona desde cero.

Los métodos registrarYLoguear y crearLista son auxiliares que llaman a los endpoints reales y quedan fuera del fragmento.

  • @Container arranca el contenedor antes de las pruebas y lo elimina al terminar.
  • @DynamicPropertySource le entrega a Spring la URL, el usuario y la clave del contenedor antes de crear el contexto; por eso no se escriben en application.properties.
  • La solicitud atraviesa el filtro JWT, SecurityConfig, el Controller, el Service, JPA y PostgreSQL. Es la cadena completa, sin mocks.
  • Los tests de una clase comparten la base, así que cada uno usa emails distintos para no chocar entre sí.

La clase del TP3 comprueba cinco casos:

Caso Resultado esperado
Login con credenciales válidas 200 con un token
Login con credenciales inválidas 401
Listar listas sin token 401
Acceder a una lista propia 200
Acceder a una lista ajena 403

Faltan casos que la matriz de acceso de la guía anterior pide: ADMIN sobre una lista ajena, destino ajeno al mover favoritos y el acceso a favoritos de otra persona.

Dependencias de pruebas en Spring Boot 4

En Spring Boot 4, @AutoConfigureMockMvc vive en un módulo aparte, spring-boot-starter-webmvc-test, que spring-boot-starter-test ya no trae. Con Testcontainers 2.x los artefactos se llaman testcontainers-junit-jupiter y testcontainers-postgresql, y PostgreSQLContainer es una clase sin parámetro de tipo. Si falta alguna dependencia, el proyecto no compila las pruebas.

Estas pruebas necesitan Docker en ejecución. Si no está disponible, el contenedor no arranca y las pruebas fallan antes de empezar.

5. Cómo Maven descubre y ejecuta las pruebas

Sección titulada «5. Cómo Maven descubre y ejecuta las pruebas»

Escribir una prueba no garantiza que alguien la ejecute. Maven corre las pruebas durante su ciclo de vida, y cada plugin decide por el nombre de la clase cuáles son suyas.

Plugin Fase en la que corre Clases que reconoce por defecto
Surefire test **/Test*.java, **/*Test.java, **/*Tests.java, **/*TestCase.java
Failsafe integration-test y verify **/IT*.java, **/*IT.java, **/*ITCase.java

Cada comando ejecuta todas las fases anteriores del ciclo:

Comando Qué ejecuta
./mvnw test Compila y corre las clases que reconoce Surefire.
./mvnw verify Todo lo anterior, más Failsafe si está configurado, y falla si alguna prueba falló.

ListaControllerIT termina en IT: no coincide con ningún patrón de Surefire, así que ./mvnw test no la ejecuta. En el repositorio de ejemplo se resolvió con la primera de las opciones de abajo: se declara Failsafe en el pom.xml y la clase la ejecuta ./mvnw verify. Una prueba que nadie ejecuta da una falsa sensación de seguridad.

Hay tres formas de resolverlo:

  1. Agregar Failsafe y usar ./mvnw verify. Separa las pruebas rápidas de las lentas:

  2. Configurar Surefire para que incluya también las clases *IT, con <include>**/*IT.java</include> dentro de <includes>, de modo que ./mvnw test las ejecute.

  3. Renombrar la clase, por ejemplo a ListaControllerTest, para que Surefire la reconozca.

Para comprobar que una prueba corre, buscá su clase en la salida de Maven, en las líneas Tests run. También se puede forzar una clase concreta con ./mvnw test -Dtest=ListaControllerIT.

Un resultado verde no demuestra que se probó lo que creés

Un build puede terminar en verde porque ninguna prueba falló, o porque la prueba importante nunca se ejecutó. Antes de confiar en una verificación automática, comprobá que realmente corre y que falla cuando se rompe la regla que debería proteger.

6. Integración continua

Sección titulada «6. Integración continua»

Si cada persona prueba únicamente en su máquina, pueden pasar días hasta descubrir que los cambios de dos personas no funcionan juntos, o que algo “andaba en mi equipo” por una configuración local.

La integración continua (CI) consiste en integrar los cambios con frecuencia y verificarlos de forma automática y reproducible en un entorno limpio, cada vez que se sube código. El resultado es una señal simple: pasó o falló.

Para el TP3, el pipeline debería verificar, como mínimo:

  • que el proyecto compila;
  • que las pruebas unitarias pasan;
  • que las pruebas de integración pasan, lo que incluye aplicar todas las migraciones sobre una base limpia;
  • que, si algo falla, el informe indica qué.

CI, entrega continua y despliegue continuo

Sección titulada «CI, entrega continua y despliegue continuo»

Son prácticas distintas y se suelen confundir. Un CI en verde no significa que algo se haya desplegado.

Práctica Qué automatiza Decisión humana
Integración continua Compilar y probar cada cambio. Revisar y fusionar.
Entrega continua Dejar un artefacto probado y listo para desplegar. Aprobar el despliegue.
Despliegue continuo Desplegar automáticamente cuando todo pasa. Ninguna en cada cambio.

Un workflow de GitHub Actions

Sección titulada «Un workflow de GitHub Actions»

GitHub Actions ejecuta flujos de trabajo definidos en archivos YAML dentro de .github/workflows/. Un primer flujo para este proyecto podría ser:

  • on define qué evento lo dispara: un push o un pull request.
  • runs-on elige la máquina virtual limpia donde corre.
  • actions/checkout descarga el código y actions/setup-java instala el JDK. La versión debe coincidir con java.version del pom.xml. cache: maven reutiliza las dependencias descargadas entre ejecuciones.
  • --batch-mode evita la salida interactiva de Maven, que estorba en un entorno automático.
  • verify ejecuta el ciclo completo; con Failsafe configurado, incluye las pruebas de integración. Con test, esas pruebas podrían quedar afuera.

El objetivo no es memorizar el YAML, sino saber qué verifica cada paso.

Tres obstáculos frecuentes

Sección titulada «Tres obstáculos frecuentes»
  • ./mvnw: Permission denied. El archivo mvnw necesita permiso de ejecución en Linux. En un repositorio creado desde Windows suele subirse sin él. Se corrige una vez con git update-index --chmod=+x mvnw y un commit.
  • Pruebas que dependen de tu máquina. Una prueba que levanta toda la aplicación, como DemoApplicationTests, la que genera Spring Initializr, se conecta a la base de application.properties. En tu equipo funciona porque hay un PostgreSQL local; en el entorno limpio del CI esa base no existe y la prueba falla. Toda prueba que cargue Spring debe obtener su base de Testcontainers, o eliminarse si no aporta nada que otra prueba ya cubra.
  • Docker para Testcontainers. Los runners de GitHub con Ubuntu incluyen Docker, por lo que Testcontainers funciona sin configuración adicional. En una máquina propia de integración continua habría que instalarlo.

Leer y usar el resultado

Sección titulada «Leer y usar el resultado»
  • En la pestaña Actions del repositorio, cada ejecución muestra sus pasos y un registro por paso. El paso de Maven contiene el informe de las pruebas fallidas.
  • Junto a cada commit y cada pull request aparece una marca verde o roja.
  • La ejecución local de ./mvnw verify debería dar el mismo resultado que el entorno automático: es la forma de reproducir un fallo.
  • GitHub permite exigir que el chequeo pase antes de fusionar, mediante reglas de protección de rama.

Comprobar que el pipeline detecta errores es parte de la tarea: se rompe una aserción a propósito, se sube el cambio, se verifica que el resultado sea rojo y luego se corrige hasta volver al verde.

Qué no resuelve la integración continua

Un CI en verde solo garantiza lo que las pruebas comprueban. No reemplaza revisar el código, no despliega la aplicación y no valida que la regla correcta esté escrita. Las credenciales reales no se escriben en el repositorio ni en el workflow: las pruebas usan una base descartable y, cuando hagan falta secretos, se guardan en los secrets de GitHub.
