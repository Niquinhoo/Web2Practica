Despliegue automático y diagnóstico

La integración continua termina en verde, pero la aplicación sigue funcionando únicamente en una computadora. Desplegar es dejarla disponible en una URL pública, con su base de datos y su configuración, de una forma que se pueda repetir. El despliegue automático convierte ese paso manual en una etapa más del pipeline: si las verificaciones pasan, la nueva versión se publica sin que nadie copie archivos a mano.

En este apunte veremos:

  • qué cambia cuando la aplicación sale de la máquina de desarrollo;
  • configuración por ambiente y manejo de secretos;
  • del despliegue manual al automático, encadenado con la integración continua;
  • cómo verificar un despliegue y diagnosticarlo cuando falla.

1. Qué cambia al salir de tu máquina

Sección titulada «1. Qué cambia al salir de tu máquina»

La aplicación y la base de datos pasan a ser servicios separados que alguien más ejecuta. El código no debe suponer nada del entorno: lo recibe desde afuera.

Aspecto En desarrollo Desplegada
Proceso ./mvnw spring-boot:run desde el IDE o la terminal Un artefacto ejecutable arrancado por la plataforma
Base de datos PostgreSQL local o en Docker Un servicio de base remoto
Configuración Valores por defecto en application.properties Variables de entorno de la plataforma
Puerto Fijo, 8080 El que asigna la plataforma
Acceso localhost, sin HTTPS URL pública con HTTPS
Datos De prueba Reales

2. El artefacto: un JAR ejecutable

Sección titulada «2. El artefacto: un JAR ejecutable»

Spring Boot empaqueta la aplicación, con su servidor web embebido, en un único archivo:

package ejecuta antes las pruebas, así que un artefacto solo se genera si pasan. Omitirlas con -DskipTests es una excepción para diagnosticar, no un hábito.

La plataforma puede construir ese archivo a partir del código fuente o ejecutar una imagen de contenedor que vos definís con un Dockerfile. En ambos casos la versión de Java del entorno de construcción y de ejecución debe coincidir con la del proyecto, java.version en el pom.xml: es una causa frecuente de fallos antes de arrancar.

3. Configuración por ambiente y secretos

Sección titulada «3. Configuración por ambiente y secretos»

La aplicación debe poder ejecutarse en cualquier ambiente sin modificar el código. El patrón del TP3 es ${VARIABLE:valorPorDefecto}: en local se usa el valor por defecto y, desplegada, la plataforma define la variable.

Variable Qué contiene ¿Es secreto?
DB_URL Dirección de la base de datos No es secreta, pero cambia en cada ambiente
DB_USERNAME Usuario de la base Conviene tratarlo como reservado
DB_PASSWORD Contraseña de la base Sí
JWT_SECRETO Clave con la que se firman los tokens Sí: quien la conozca puede fabricar tokens
JWT_VIGENCIA_MINUTOS Duración del token No

Algunas reglas:

  • Los secretos no se escriben en el repositorio, en el workflow ni en los logs. Se cargan en el panel de variables de la plataforma y, para el pipeline, en los secrets de GitHub.
  • Los valores por defecto sirven para desarrollo, no para producción. Si en un ambiente real falta JWT_SECRETO y la aplicación usa la clave de ejemplo, cualquiera que lea este repositorio podría emitir tokens válidos. Es preferible que la aplicación falle al arrancar si falta un secreto. Una forma es no declarar valor por defecto en el perfil de producción: Spring no puede resolver el marcador y detiene el arranque.
  • Un ambiente tiene sus propias credenciales. La clave de la base de pruebas no debe ser la de la base real, ni la del desarrollo.
  • Un perfil de Spring permite agrupar configuración por ambiente en archivos como application-prod.properties y activarlo con la variable SPRING_PROFILES_ACTIVE.

La plataforma también define el puerto. Si no es 8080, la aplicación debe escuchar donde se le indique:

La dirección de la base casi nunca viene lista para JDBC

Muchas plataformas entregan la conexión como una URL del tipo postgres://usuario:clave@host:5432/base. JDBC necesita otro formato: jdbc:postgresql://host:5432/base, con el usuario y la clave en variables separadas. Además, las bases administradas suelen exigir conexión cifrada, lo que se indica con ?sslmode=require al final de la URL. Si la aplicación arranca y cae con un error de conexión, revisá primero esto.

La Twelve-Factor App formuló esta idea como principio: la configuración que cambia entre ambientes vive en el entorno, no en el código.

4. Migraciones sobre la base remota

Sección titulada «4. Migraciones sobre la base remota»

Flyway se ejecuta al arrancar la aplicación contra la base que indique la configuración. En la primera puesta en marcha, la base remota está vacía y Flyway aplica las migraciones V1 a V6. Se puede comprobar en la tabla flyway_schema_history.

Dos consecuencias importan en un despliegue:

  • Si una migración falla, la aplicación no arranca. El log de Flyway indica cuál. Es mejor que arrancar con un esquema a medias.
  • Las migraciones solo avanzan. Volver a una versión anterior de la aplicación no deshace las migraciones ya aplicadas. Por eso conviene que cada cambio de esquema sea compatible con la versión previa del código, como el orden columna opcional, completar datos, restricción de Migraciones y rendimiento.

La base remota tiene su propio historial: una migración ya aplicada allí no se edita, por la misma razón del checksum que vimos en la Unidad 2.

5. Del despliegue manual al automático

Sección titulada «5. Del despliegue manual al automático»
Manual Automático
Qué hace la persona Compila, sube el archivo, carga la configuración y reinicia Sube el código al repositorio
Repetibilidad Depende de recordar cada paso Los mismos pasos, siempre
Verificación previa Opcional y fácil de saltear Una condición del pipeline
Riesgo típico Un paso olvidado, una versión equivocada Publicar algo roto si el pipeline no frena

Como vimos en Pruebas e integración continua, el despliegue continuo publica cada cambio que pasa las verificaciones sin pedir aprobación; en la entrega continua hay una aprobación humana antes del último paso. Lo que se automatiza es el mismo recorrido.

Hay dos formas habituales de lograrlo:

  1. La plataforma se conecta al repositorio. Cada subida a una rama dispara su propia construcción y publicación. Es lo más simple, pero hay que asegurarse de que no publique una versión cuyas pruebas fallaron. Algunas plataformas permiten esperar a que los chequeos de CI terminen en verde antes de desplegar: en Render es la opción After CI Checks Pass, que en un render.yaml se escribe autoDeployTrigger: checksPass.
  2. El pipeline ordena el despliegue. Un trabajo adicional del workflow se ejecuta únicamente si el anterior pasó y le pide a la plataforma que publique, mediante una dirección de despliegue o una herramienta de línea de comandos. Se ve exactamente qué se verificó antes de publicar.

El segundo caso se expresa extendiendo el ci.yml del apunte anterior:

  • needs: verificar hace que desplegar espere al otro trabajo y no se ejecute si falló.
  • if limita el despliegue a las subidas a la rama principal: un pull request se prueba, pero no se publica.
  • La dirección que dispara el despliegue es un secreto y se guarda en los secrets del repositorio. La URL pública, que no lo es, puede ir en una variable.
  • El último paso es una comprobación de humo: publicar no significa que la aplicación haya arrancado. Como el arranque tarda, curl reintenta antes de dar el paso por fallido.

El detalle del comando de despliegue depende de la plataforma; el proveedor es un ejemplo intercambiable y la estructura del pipeline es la misma. En Render, por ejemplo, la dirección que dispara el despliegue es el deploy hook del servicio: un POST a esa URL secreta inicia el despliegue.

6. Verificar el despliegue

Sección titulada «6. Verificar el despliegue»

Una versión está desplegada cuando responde correctamente desde su URL pública. Para el TP3 alcanzan tres comprobaciones:

Comprobación Resultado esperado Qué demuestra
GET /health 200 La aplicación arrancó y escucha en el puerto correcto.
GET /api/listas sin token 401 La seguridad está activa en el ambiente desplegado.
GET /api/listas con un token válido 200 La base está conectada y las migraciones se aplicaron.

El endpoint de estado debe ser público y mínimo: confirma que la aplicación vive sin revelar la versión, la configuración ni detalles de la base. Cualquier persona o servicio de monitoreo puede consultarlo, así que no debe exponer datos internos. Spring Boot Actuator ofrece un endpoint de este tipo ya hecho; el TP usa uno propio y simple.

7. Diagnosticar un despliegue que falla

Sección titulada «7. Diagnosticar un despliegue que falla»

Cuando algo falla, primero se identifica en qué etapa ocurrió. Cada una deja pistas en un lugar distinto.

Síntoma Causa probable Dónde mirar
Falla antes de arrancar No compila, una prueba falla, versión de Java distinta, mvnw sin permiso de ejecución El log de construcción de la plataforma o del pipeline
Arranca y se detiene enseguida Falta una variable de entorno, el marcador ${...} no se resolvió, se rechazó la conexión El log de arranque; buscar el primer error, no el último
Se detiene en la migración Un SQL inválido o una migración ya aplicada que fue modificada El log de Flyway, con el número de la migración
502 o 503 de la plataforma La aplicación no responde en el puerto que la plataforma espera La variable PORT y server.port
401 con un token que antes funcionaba Cambió JWT_SECRETO, o el token venció Variables de entorno y fecha de emisión del token
403 inesperado Token de otro usuario, o rol desactualizado dentro del token El payload del token y la regla de propiedad

Los logs son la salida estándar de la aplicación que captura la plataforma. Sirven para reconstruir qué pasó, pero también pueden filtrar datos: nunca deben contener contraseñas, tokens ni secretos.

Los logs y el endpoint de estado son el punto de partida. Para sistemas más grandes existen otras señales: las métricas cuentan cuánto y con qué rapidez ocurre algo, de forma agregada, y las trazas siguen el recorrido de una solicitud entre varios servicios. Acá las mencionamos para comparar; el TP no exige instalar una plataforma de observabilidad.

Un proveedor gratuito no es una arquitectura de producción

Los planes gratuitos suelen tener límites: algunos suspenden el servicio tras un tiempo sin tráfico y la primera solicitud tarda más, y no siempre garantizan copias de seguridad. Sirven para la experiencia del TP, donde alcanza con la evidencia de que el despliegue funcionó, no para sostener datos reales.
