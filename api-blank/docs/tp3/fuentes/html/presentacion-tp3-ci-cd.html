Bloque 1 · Pruebas y coberturaConsigna 5.1

Prueba unitaria: cómo es

@ExtendWith(MockitoExtension.class)
class ListaServiceImplTest {

    @Mock private ListaRepository listaRepository;
    @Mock private FavoritoRepository favoritoRepository;
    @Mock private ContextoSeguridad contextoSeguridad;

    @Test
    void obtener_listaAjena_lanzaAccesoDenegado() {
        // Preparación
        when(listaRepository.findById(7L))
            .thenReturn(Optional.of(new Lista(7L, "De Ana", ANA)));
        when(contextoSeguridad.usuarioActualId()).thenReturn(BOB);
        when(contextoSeguridad.esAdmin()).thenReturn(false);

        // Acción y verificación
        assertThatThrownBy(() -> service.obtener(7L))
            .isInstanceOf(AccesoDenegadoException.class);
    }
}
  1. Preparar: armamos el escenario con datos de prueba (when … thenReturn).
  2. Actuar: llamamos al método que queremos probar.
  3. Verificar: afirmamos qué debe pasar (assertThat…). Si no se cumple, la prueba falla.
  • Mockito simula el repository y el contexto de seguridad: no hay Spring ni base y corre en milisegundos.
  • Se puede porque el Service depende de interfaces, no de JPA.

class ListaControllerIT {

        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);

  1. Testcontainers arranca un PostgreSQL real en Docker y lo destruye al terminar.
  2. Flyway aplica las migraciones V1 a V6 sobre esa base limpia.

¿Cómo se ejecutan las pruebas? Paso a paso

  1. Abrí una terminal en la carpeta del proyecto (la que tiene el pom.xml). Para las de integración, Docker Desktop tiene que estar abierto.
  2. Solo las unitarias (rápido, sin Docker): ./mvnw clean test
  3. Todo: unitarias, integración, reporte y umbral: ./mvnw clean verify
  4. Leé el final de la salida: la línea Tests run: y después BUILD SUCCESS o BUILD FAILURE.
SufijoLo ejecutaCon el comando
*TestSurefiretest y verify
*ITFailsafesolo verify
Todo bien · ./mvnw clean test Tests run: 29, Failures: 0, Errors: 0, Skipped: 0 BUILD SUCCESS Algo falló · ejemplo (simplificado) [ERROR] ListaServiceImplTest [ERROR] .obtener_listaAjena_lanzaAccesoDenegado BUILD FAILURE
  • mvn test no corre las *IT: para ellas, verify. En Windows, si ./mvnw no responde, usá .\mvnw.cmd.

  1. Generalo con ./mvnw clean verify (Docker abierto): corre todas las pruebas y arma el reporte al final.

Bloque 1 · CoberturaJaCoCo 3 de 6

¿Cómo se lee el reporte? Cuatro clics

  1. Total: la fila de abajo de index.html. El umbral mira la columna Lines.
  2. Un paquete, por ejemplo com.example.demo.service: una fila por clase.
  3. Una clase, por ejemplo ListaServiceImpl: una fila por método.
  4. Un método: el código fuente pintado de colores. Ahí se ve qué falta probar.
Cada columna: lo que falta y el porcentaje Missed es lo que ninguna prueba ejecutó y Cov. el porcentaje cubierto. La barra es roja en lo que falta y verde en lo cubierto.
  • Verde: la línea se ejecutó.
  • Amarillo: se ejecutó, pero un if solo se probó por un lado.
  • Rojo: ninguna prueba llegó hasta esa línea.
  • Miramos Lines (lo que mide el umbral) y Branches (los if).

¿Qué significa cada columna del reporte?

ColumnaQué cuenta
ElementEl paquete. Con un clic se abre la clase y después el método.
InstructionsLo más fino del código compilado. Missed: ninguna prueba lo ejecutó. Cov.: el porcentaje ejecutado.
BranchesLos caminos de cada if: se prueba el verdadero y el falso. n/a: no hay if.

LinesLíneas de código. Missed: sin ejecutar. El otro número es el total. La que usa el umbral.
MethodsMétodos que ninguna prueba llamó, sobre el total.

  • La barra: roja es lo que falta y verde lo cubierto; su largo es proporcional al tamaño del paquete.
  • Para empezar alcanza con Lines y Branches.

Opcional: que el build falle si la cobertura baja

<execution>
    <id>umbral-minimo</id>
    <phase>verify</phase>
    <goals><goal>check</goal></goals>
    <configuration>
        <rules><rule>
            <element>BUNDLE</element>
            <limits><limit>
                <counter>LINE</counter>
                <value>COVEREDRATIO</value>
                <minimum>${cobertura.minima}</minimum>
            </limit></limits>
        </rule></rules>
    </configuration>
</execution>
cobertura.minima = 0.60 → pasa All coverage checks have been met. BUILD SUCCESS cobertura.minima = 0.90 → falla Rule violated for bundle demo: lines covered ratio is 0.63, but expected minimum is 0.90 BUILD FAILURE
  • check corre en verify: si la cobertura de líneas baja del mínimo, el build falla y el CI queda en rojo. El mínimo es la propiedad cobertura.minima del pom.xml.
  • Un umbral razonable (60 %) frena la regresión sin empujar a escribir pruebas vacías solo para llegar al número.
Bloque 2 · Integración continuaConsigna 6

¿Qué es la integración continua (CI)?

  • Sin CI: cada persona prueba en su máquina, con su base y su configuración. Pueden pasar días hasta descubrir que dos cambios no funcionan juntos.
  • Con CI: cada push dispara el mismo recorrido en un entorno limpio y devuelve una señal simple: verde o rojo.
  • En el TP3 verifica cuatro cosas: que compila, que pasan las unitarias, que pasan las de integración y que la cobertura llega al mínimo.
Bloque 2 · Integración continuaConsigna 6.1

Armar el ci.yml, paso a paso (1 de 2): el esqueleto

  1. Creá el archivo .github/workflows/ci.yml, en la raíz del repo (junto al pom.xml). Es un archivo más del proyecto: se edita en VS Code.
  2. Nombre y disparador: name y on. Acá corre en cada push y en cada pull request.
  3. Un job: dentro de jobs, uno llamado verificar. runs-on: ubuntu-latest pide una máquina limpia, que ya trae Docker.
  4. Dos pasos de preparación: checkout baja el código y setup-java instala Java 25, la misma versión del pom.xml, con caché de Maven.
name: CI

on:
  push:
  pull_request:

jobs:
  verificar:
    name: Compilar y probar
    runs-on: ubuntu-latest
    steps:
      - name: Descargar el código
        uses: actions/checkout@v6

      - name: Instalar Java 25
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '25'
          cache: maven
Bloque 2 · Integración continuaConsigna 6.1

Armar el ci.yml, paso a paso (2 de 2): las pruebas

  1. Un paso por cada cosa que querés verificar, con run: ./mvnw …. Así se ve en cuál falla.
  2. Guardá lo que quieras revisar con upload-artifact. if: always() lo sube aunque algo falle.
  3. Opcional: un paso que escribe el total de cobertura en el resumen de la ejecución.
  4. Commit y push: GitHub detecta el archivo y lo ejecuta solo. No hay nada que instalar ni activar.
  • El paso 3 repite las unitarias y suma las de integración (Failsafe, *IT) y el reporte y umbral de JaCoCo: por eso el reporte se genera ahí.
      - name: 1 · Compilar el proyecto y las pruebas
        run: ./mvnw --batch-mode test-compile

      - name: 2 · Pruebas unitarias
        run: ./mvnw --batch-mode test

      - name: 3 · Pruebas de integración y cobertura
        run: ./mvnw --batch-mode verify

      - name: Guardar el reporte de cobertura
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: reporte-de-cobertura
          path: target/site/jacoco
Bloque 2 · Integración continuaConsigna 6

¿Cómo se ejecuta el CI? Paso a paso

  1. Publicá el repositorio desde GitHub Desktop (Publish repository, puede ser privado). El archivo ci.yml viaja en ese primer envío.
  2. En github.com, abrí el repo → pestaña Actions. Ya hay una ejecución de CI: arrancó sola.
  3. Entrá a la ejecución → job Compilar y probar: cada paso (1 · Compilar, 2 · Pruebas unitarias, 3 · Pruebas de integración y cobertura) se despliega con su registro.
  4. Si hay una ✗, abrí ese paso: ahí está la prueba que falló, igual que en tu terminal.
  5. El resumen de la ejecución muestra el total de cobertura. Abajo, en Artifacts: descargá reporte-de-cobertura, un zip con el index.html de JaCoCo.
Recorrido de clics Repo → Actions → CI → Compilar y probar → paso con ✗ → registro Estados de una ejecución ● amarillo en curso ✓ verde todo pasó ✗ rojo algo falló
  • No hay botón de "ejecutar": cada push o pull request dispara una ejecución nueva.
  • Re-run jobs, arriba a la derecha, repite la ejecución sin hacer otro commit.

Cuando el CI sale rojo: leerlo y arreglarlo

Pasa en mi máquina, falla en el CI DemoApplicationTests, la prueba que genera Spring Initializr, levanta toda la aplicación contra la base de application.properties: localhost:5432. En tu equipo hay un PostgreSQL; en el runner limpio no, y el contexto no arranca.
  • El arreglo: toda prueba que cargue Spring obtiene su base de Testcontainers, o se elimina si no aporta. Acá se elimina: ListaControllerIT ya carga el contexto completo contra su propia base.
  • Si el paso de Maven falla con ./mvnw: Permission denied: git update-index --chmod=+x mvnw y subí el cambio.
  1. Primer envío con el pipeline y DemoApplicationTests todavía en el proyecto → Actions: rojo.
  2. Abrí el paso fallido: el registro dice que la aplicación no pudo conectarse a localhost:5432.
  3. Enviá el arreglo, la versión sin esa prueba → verde.
  4. Consigna 6.2: cambiá isForbidden() por isOk() en accederAListaAjena_devuelve403 y enviá → rojo. Revertí → verde.
Bloque 3 · Despliegue automáticoConsigna 7

¿Cómo funciona? Del push a la URL pública

  • Un CI en verde no publica nada solo: hay que conectarlo con la plataforma. Render mira ese mismo chequeo de GitHub.
  • Si pasa: Render construye la imagen con el Dockerfile, arranca la instancia nueva, espera que /health responda y recién entonces le pasa el tráfico.
  • Si falla el CI o el arranque: no se publica nada y la versión anterior sigue en pie.
  • Nadie copia archivos ni aprueba a mano: es despliegue continuo. Un pull request se prueba pero no se publica: Render solo mira main.

Preparar la aplicación: Dockerfile y variables

# Etapa 1: compilar el JAR (las pruebas ya corrieron en la CI)
FROM eclipse-temurin:25-jdk AS build
WORKDIR /app
COPY . .
RUN ./mvnw -B -DskipTests package

# Etapa 2: imagen final, solo con el JRE y el JAR
FROM eclipse-temurin:25-jre
WORKDIR /app
RUN groupadd --system app && useradd --system --gid app app
COPY --from=build /app/target/*.jar app.jar
USER app
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75.0", "-jar", "app.jar"]
VariablePara qué
PORTPuerto que asigna Render (por defecto 10000); server.port=${PORT:8080}
DB_URLBase remota, en formato JDBC
DB_USERNAME, DB_PASSWORDCredenciales de la base
JWT_SECRETOClave para firmar tokens
  • El ${VARIABLE:valorPorDefecto} de application.properties deja que el proyecto siga andando en local y que la plataforma lo reconfigure sin tocar el código.
  • Render ejecuta el Dockerfile del repo: así la versión de Java la fijamos nosotros. La app debe escuchar en 0.0.0.0 y en PORT, y Spring Boot ya lo hace.
  • La imagen no lleva secretos: el JWT_SECRETO de ejemplo es solo para desarrollo.

Armar el render.yaml, paso a paso (1 de 2): el servicio web

  1. Creá el archivo render.yaml en la raíz del repo, junto al Dockerfile.
  2. Declará el servicio web: type: web, un name y plan: free.
  3. Decile cómo construirlo: runtime: docker y dockerfilePath. Render usa nuestro Dockerfile.
  4. Chequeo de salud: healthCheckPath: /health. La versión nueva recibe tráfico recién cuando esa ruta responde.
  5. La línea que automatiza todo: autoDeployTrigger: checksPass despliega solo si el CI de GitHub pasa. Otros valores: commit (siempre) y off.
services:
  - type: web
    name: web2-demo
    runtime: docker
    plan: free
    dockerfilePath: ./Dockerfile
    healthCheckPath: /health
    autoDeployTrigger: checksPass

Armar el render.yaml, paso a paso (2 de 2): variables y base de datos

  1. Variables de entorno en envVars: las que la aplicación lee (DB_URL, DB_USERNAME, DB_PASSWORD, JWT_SECRETO).
  2. sync: false en DB_URL: el valor se pide una sola vez, al crear el Blueprint.
  3. fromDatabase en usuario y clave: salen de la base declarada abajo y no se escriben en ningún archivo.
  4. generateValue: true en JWT_SECRETO: Render inventa una clave aleatoria.
  5. La base, en databases: PostgreSQL descrita como código y versionada con la aplicación.
    envVars:

        sync: false
      - key: DB_USERNAME
        fromDatabase:
          name: web2-db
          property: user
      # DB_PASSWORD: igual, con property: password
      - key: JWT_SECRETO
        generateValue: true

databases:

    plan: free
    databaseName: web2
    user: web2
Bloque 3 · Render, paso 1 de 4Consigna 7.1

Crear el Blueprint en Render

  1. Antes: el CI tiene que estar en verde en main. Render espera ese chequeo para desplegar.
  2. En render.com, entrá con tu cuenta de GitHub → New → Blueprint.
  3. Conectá GitHub: autorizá a Render y elegí el repositorio (sirve con repos privados). Rama: main.
  4. Render lee render.yaml y lista lo que va a crear. Pide DB_URL: escribí pendiente y confirmá con Deploy Blueprint.
  5. Esperá: se crean la base y el servicio. El panel muestra Failed deploy en rojo, y es lo esperado: el primer despliegue todavía no sabe dónde está la base.
Qué crea el Blueprint web2-db PostgreSQL (plan free) web2-demo Web Service (Docker) Variables de entorno DB_USERNAME // sale de la base DB_PASSWORD // sale de la base JWT_SECRETO // la genera Render DB_URL // la completás vos, después
  • Dos recursos, no uno: web2-demo es la aplicación y web2-db es su base PostgreSQL. Render los lista juntos y los dos tienen que figurar en marcha (la base como Available).
  • Por qué DB_URL queda para después: fromDatabase entrega usuario y clave, pero no el nombre de host, que recién existe cuando la base ya está creada.

DB_URL en formato JDBC jdbc:postgresql://HOSTNAME:5432/DATABASE?sslmode=require
  • El nombre de la base no es web2: Render le agrega un sufijo y queda, por ejemplo, web2_s4fo. Usá el que muestra Database.
  • La URL que muestra Render empieza con postgresql:// y trae usuario y clave: no sirve tal cual para JDBC. Por eso se arma a mano y el usuario y la clave van en variables aparte.
  • El host interno solo se alcanza desde servicios de Render de la misma región: es el recomendado. Desde tu PC se usa la URL externa, que exige sslmode=require.

checksPass o deploy hook: dos formas de lo mismo

  desplegar:
    needs: verificar
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - name: Pedir el despliegue a Render
        run: curl --fail -X POST "${{ secrets.RENDER_DEPLOY_HOOK_URL }}"
checksPassDeploy hook
Dónde vive la reglaEn render.yamlEn el workflow (needs + if)
Secretos extraNingunoRENDER_DEPLOY_HOOK_URL
autoDeployTriggerchecksPassoff
Se ve enPanel de RenderLa pestaña Actions
  • El deploy hook es una URL secreta del servicio (Settings): un POST inicia el despliegue.
  • Con el hook, needs: verificar garantiza el orden y if limita el despliegue a main. Hay que dejar autoDeployTrigger: off para no desplegar dos veces.
  • Nosotros usamos checksPass: hay menos que configurar y la plataforma ya sabe leer el chequeo de GitHub.
