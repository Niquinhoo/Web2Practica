Autenticación y autorización en una API

Hasta el TP2, cualquier persona que conociera la URL podía listar, leer o borrar cualquier lista. Al incorporar usuarios, la API debe poder responder quién hace cada solicitud y si esa persona puede hacer eso sobre ese recurso.

La Unidad 1 comparó sesiones, tokens opacos y JWT, y presentó los modelos RBAC, ABAC y ReBAC en Estado, integración y protección de APIs. Acá aplicamos esas ideas a una solicitud real del TP3: registro, login, solicitud con token y regla de acceso.

En este apunte veremos:

  • cómo guardar credenciales y verificar un login;
  • el ciclo de vida de un JWT: emisión, validación en cada solicitud y límites;
  • dónde se separan la autenticación y la autorización en el recorrido de una solicitud;
  • cómo ubicar la propiedad y los roles, y qué cubre una matriz de acceso.

1. El dominio ahora tiene dueño

Sección titulada «1. El dominio ahora tiene dueño»

El TP3 agrega una relación por encima de las que ya existían. Cada lista pertenece a un usuario, y los favoritos cuelgan de las listas.

Un usuario tiene un rol, USER o ADMIN, y la base guarda solo lo necesario para verificarlo:

No todas las rutas exigen identidad. El catálogo de productos es una lectura pública y /api/auth/** es justamente el lugar donde se obtiene la identidad.

Ruta Quién puede entrar
/api/auth/** Cualquier persona: registro y login.
/api/productos/**, /health, /ping, Swagger Cualquier persona: lectura pública y documentación.
/api/listas/**, /api/favoritos/** Solo quien presenta un token válido. En listas, además, rige la regla de propiedad.

2. Autenticar y autorizar son preguntas distintas

Autenticación Autorización
Pregunta ¿Quién realiza la solicitud? ¿Puede esa identidad hacer esto sobre este recurso?
Se apoya en Credenciales o un token Un rol, la propiedad del recurso u otro atributo
Si falla 401 Unauthorized 403 Forbidden
Dónde vive en el TP JwtAuthenticationFilter y SecurityConfig ListaServiceImpl

Estar autenticado no alcanza: una persona con un token válido sigue sin poder leer la lista de otra.

3. Credenciales: guardar un hash, nunca la contraseña

Sección titulada «3. Credenciales: guardar un hash, nunca la contraseña»

Si alguien obtuviera una copia de la base y las contraseñas estuvieran guardadas tal cual, quedarían expuestas todas las cuentas, y las de otros sitios en los que las personas reutilizan la misma clave.

Por eso la aplicación no conserva la contraseña. Guarda el resultado de aplicarle una función pensada para este uso:

  • es de un solo sentido: no existe una operación para recuperar el texto original;
  • usa una sal (salt) aleatoria por usuario, de modo que dos contraseñas iguales produzcan hashes distintos;
  • tiene un costo configurable: es lenta a propósito, para encarecer los intentos de adivinarla.

Para verificar un login, la aplicación recalcula el hash con la sal guardada y compara. Un hash rápido de propósito general, como SHA-256 aplicado a secas, no cumple con esas propiedades.

Cuatro decisiones del código merecen explicación:

  • El rol no lo elige el cliente. RegistroRequest solo tiene email y password, y el Service asigna siempre USER. Si el rol llegara en el cuerpo, cualquiera podría registrarse como ADMIN.
  • La respuesta no incluye el hash. UsuarioResponse expone id, email y rol.
  • El email repetido responde 409. La comprobación previa con existsByEmail da un mensaje claro, pero no reemplaza la restricción UNIQUE de la tabla: dos registros simultáneos podrían pasar la comprobación y solo la base garantiza la unicidad. Lo vimos en Transacciones y concurrencia.
  • Se valida la entrada. RegistroRequest usa @Email y @Size(min = 8); esa validación evita datos mal formados, pero no decide quién puede hacer qué.

BCrypt es la tecnología del ejemplo, no la única opción

El requisito es usar un algoritmo diseñado para contraseñas, con sal y costo. BCrypt es una opción madura y está disponible en Spring Security, pero la guía de OWASP sobre almacenamiento de contraseñas prioriza Argon2id para sistemas nuevos. Cambiar de algoritmo no debería obligar a tocar el Service: por eso PasswordEncoder es una abstracción.

4. Login y JWT

Sección titulada «4. Login y JWT»

El login verifica las credenciales y, si son correctas, emite un token:

El mensaje es el mismo cuando el email no existe y cuando la contraseña es incorrecta. Si fueran distintos, la API permitiría averiguar qué emails tienen cuenta. En ambos casos la respuesta es 401.

Qué lleva el token

Sección titulada «Qué lleva el token»

Un JWT son tres segmentos, cabecera.payload.firma. Al decodificar el central, el token del TP3 muestra algo así:

sub es el id del usuario, rol es un dato propio del TP, iat es el momento de emisión y exp el de vencimiento, ambos en segundos desde 1970. El payload está codificado, no cifrado: cualquier persona que tenga el token puede leerlo, así que no debe llevar contraseñas ni datos sensibles.

Emitir y validar

Sección titulada «Emitir y validar»

La firma es un HMAC calculado con un secreto compartido: quien conoce el secreto puede emitir y verificar. Alcanza para una aplicación con un único servicio; si varias APIs debieran validar tokens sin poder emitirlos, se usarían claves asimétricas, como vimos en la Unidad 1.

parseSignedClaims exige un token firmado, verifica la firma con la clave y comprueba el vencimiento. Un token alterado, vencido o sin firma lanza una excepción.

El secreto no se escribe en el código

app.jwt.secreto se toma de una variable de entorno en application.properties. El valor por defecto del proyecto existe solo para que levante en local: en un ambiente real, la aplicación debería fallar al arrancar si falta el secreto en lugar de usar uno de ejemplo. Quien conozca el secreto puede fabricar tokens de cualquier usuario.

Qué pasa durante la vida del token

Sección titulada «Qué pasa durante la vida del token»

El servidor valida firma y vencimiento, pero no consulta la base en cada solicitud. Esa es la ventaja del JWT y también su límite:

Situación Qué ocurre con este diseño
El token venció o fue modificado No se reconoce ninguna identidad y la ruta protegida responde 401.
Se cambia el rol del usuario en la base El token ya emitido conserva el rol anterior hasta que vence o hasta un nuevo login.
El usuario cierra sesión en la aplicación cliente Borrar el token del cliente no lo invalida en el servidor: sigue siendo válido hasta su exp.
Se deshabilita o elimina al usuario El filtro no consulta la base, así que el token sigue siendo aceptado hasta vencer.
Alguien roba el token Puede actuar como esa persona hasta que venza.

Por eso los tokens de acceso tienen una vigencia corta, se transportan por HTTPS y no se escriben en los logs. Revocarlos antes de tiempo exigiría guardar estado en el servidor, por ejemplo una lista de tokens anulados, o renovar los tokens con un mecanismo de refresh; ambos quedan fuera del TP y los tratamos solo como idea.

5. Validar el token en cada solicitud

Sección titulada «5. Validar el token en cada solicitud»

El filtro lee el encabezado Authorization, valida el token y deja la identidad disponible para el resto de la solicitud:

Tres detalles ayudan a leerlo:

  • SecurityContextHolder guarda la identidad de la solicitud en curso. El principal es el id del usuario y las authorities llevan el rol con el prefijo ROLE_, que es el que Spring espera para hasRole("ADMIN").
  • El filtro autentica, no autoriza. Si el token falta o es inválido, no responde 401: deja el contexto vacío y continúa. Quien decide después si esa ruta necesitaba identidad es la configuración.
  • Por eso un token vencido en una ruta pública, como GET /api/productos, no la bloquea: la ruta no exigía identidad.

6. Qué rutas se protegen

Sección titulada «6. Qué rutas se protegen»

SecurityConfig declara qué es público, que no hay sesión y dónde se inserta el filtro:

  • Las reglas se evalúan en orden y la primera que coincide gana. Terminar con anyRequest().authenticated() hace que un endpoint nuevo quede protegido por defecto: hay que declarar explícitamente lo que es público, no lo que es privado.
  • STATELESS indica que el servidor no crea sesiones: cada solicitud se autentica sola por su token.
  • authenticationEntryPoint responde 401 cuando una ruta protegida llega sin identidad, y accessDeniedHandler responde 403 cuando la regla de acceso de Spring Security lo deniega.

Por qué se desactiva CSRF acá

Un ataque CSRF aprovecha que el navegador agrega automáticamente credenciales, como una cookie, a una solicitud que el atacante provoca desde otro sitio. En este diseño el token no viaja en una cookie: el código del cliente lo escribe a mano en el encabezado Authorization, y un sitio ajeno no puede lograr que el navegador lo agregue. Que la aplicación sea stateless no alcanza por sí solo como justificación; lo que importa es cómo viaja la credencial. Si el token se guardara en una cookie, habría que volver a analizar la protección. Está explicado en la documentación de Spring Security.

Qué pasa si agregás la dependencia y no configurás nada

Con spring-boot-starter-security en el classpath y sin una configuración propia, Spring Boot activa una seguridad por defecto: exige autenticación en todos los endpoints, incluidos los públicos y Swagger, con un usuario user y una contraseña generada que aparece en el log. La app deja de responder como antes hasta que SecurityConfig declara las reglas.

Para probar endpoints protegidos desde Swagger UI, la documentación debe declarar el esquema de seguridad. Con bearerAuth en OpenApiConfig y @SecurityRequirement(name = "bearerAuth") en los controllers protegidos aparece el botón Authorize, donde se pega el token sin el prefijo Bearer. La mecánica de OpenAPI está en Swagger y OpenAPI.

7. Autorizar: dueño y rol

Sección titulada «7. Autorizar: dueño y rol»

Superado el filtro, la API sabe quién es la persona, pero todavía no si la lista que pide le pertenece. Esa es una regla de negocio: “esta lista es tuya o no”.

El dueño lo decide el servidor

Sección titulada «El dueño lo decide el servidor»

Al crear una lista, el dueño es la persona autenticada. ListaRequest solo contiene nombre: el id del usuario nunca se toma de un dato que pueda falsificar el cliente.

La regla de propiedad

Sección titulada «La regla de propiedad»

Todas las operaciones sobre una lista puntual pasan por el mismo método:

obtener, eliminar, favoritosDe y las dos listas de moverFavoritos lo usan. Concentrar la regla en un único punto evita olvidarla en un camino de acceso. En moverFavoritos se comprueba tanto el origen como el destino: si solo se verificara el origen, alguien podría mover favoritos hacia la lista de otra persona.

Dónde ubicarla importa:

  • En el Service, no en el Controller ni en el filtro. Es una regla del negocio, vale para cualquier forma de invocar el caso de uso y se puede probar sin HTTP.
  • Combina dos modelos de la Unidad 1. El rol ADMIN es RBAC; comparar lista.usuarioId con el usuario actual es una condición sobre un atributo del recurso, propia de ABAC. Una anotación @PreAuthorize("hasRole('ADMIN')") resolvería solo la primera, porque el rol se conoce sin leer el recurso y la propiedad no.

Decisiones que conviene hacer explícitas

Sección titulada «Decisiones que conviene hacer explícitas»

403 frente a 404

La API responde 404 si la lista no existe y 403 si existe pero no es del usuario. El TP fija ese contrato. Tiene un costo: quien prueba ids distintos puede descubrir cuáles existen. HTTP permite responder 404 para ocultar la existencia de un recurso prohibido, y algunas APIs lo hacen; es una decisión de diseño, no un error. Ver RFC 9110, sección 15.5.4.

Alcance de ADMIN y listas sin dueño

En esta solución ADMIN queda eximido del control en todas las operaciones sobre listas: leer, borrar y también mover favoritos entre listas de personas distintas. Un administrador de solo lectura requeriría una política por operación. Además, usuario_id quedó opcional en la migración V6, así que las listas anteriores al TP3 no tienen dueño: la condición lista.usuarioId() != null hace que solo un ADMIN pueda acceder a ellas. Agregar una clave foránea no decide quién es el propietario de los datos existentes; esa política debe elegirse y escribirse en una migración.

8. Matriz de acceso y comprobación

Sección titulada «8. Matriz de acceso y comprobación»

Una regla de acceso no está completa hasta que se revisan todos los caminos. La matriz cruza cada operación con cada tipo de solicitante. Esto es lo que hace hoy la solución sobre las listas:

Operación Sin token Dueño Otro usuario ADMIN
GET /api/listas 401 Permitido, solo las suyas Permitido, solo las suyas Permitido, todas
POST /api/listas 401 Permitido, queda a su nombre Permitido, queda a su nombre Permitido, queda a su nombre
GET /api/listas/{id} 401 Permitido 403 Permitido
DELETE /api/listas/{id} 401 Permitido, si está vacía 403 Permitido, si está vacía
GET /api/listas/{id}/favoritos 401 Permitido 403 Permitido
POST /api/listas/{origenId}/mover-favoritos 401 Permitido si ambas listas son suyas 403 Permitido

Una parte de la matriz todavía está sin cubrir

Los endpoints de /api/favoritos exigen un token válido, pero no consultan a qué lista pertenece cada favorito ni quién es su dueño. Con la solución actual, cualquier persona autenticada podría leer o modificar un favorito de otra conociendo su id. La protección por recurso tiene que cubrir cada camino de acceso, no solo el que se probó primero. Es el mismo problema que describe OWASP como autorización a nivel de objeto; ver su guía de autorización.

9. Límites de esta solución

Sección titulada «9. Límites de esta solución»

Lo que el TP3 resuelve alcanza para el ejercicio, pero deja afuera varias cosas:

  • Revocación: un token emitido sigue siendo válido hasta vencer, y un cambio de rol no se refleja hasta el próximo login.
  • Renovación: no hay refresh tokens; al vencer, la persona debe iniciar sesión otra vez.
  • Intentos de adivinar contraseñas: el login no limita intentos. El límite de solicitudes de la Unidad 1 es la herramienta para eso.
  • Recuperación de contraseña y proveedores externos: no se implementan OAuth ni OpenID Connect ni el restablecimiento de la clave.
  • Favoritos: falta el control de propiedad descrito en la sección anterior.
  • Una sola clave: el mismo secreto firma y verifica, y su filtración compromete a todos los usuarios.
