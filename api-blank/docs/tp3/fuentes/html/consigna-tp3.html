TP3 · Seguridad, pruebas e integración continua

Autenticación, autorización, pruebas automatizadas, CI y una experiencia básica de despliegue.

📽️ TP3: autenticación, autorización y pruebas

📽️ TP3: pruebas, cobertura, CI y despliegue

Objetivos

Sección titulada «Objetivos»
  • Implementar autenticación con usuario y contraseña, emitiendo un token para las siguientes requests.
  • Aplicar autorización por rol y por propiedad de recursos: que cada usuario solo pueda operar sobre lo suyo.
  • Validar accesos permitidos y denegados con pruebas automatizadas, además de pruebas unitarias de la lógica de negocio.
  • Ejecutar esas pruebas automáticamente en cada push, incluyendo las migraciones contra una base limpia.
  • Desplegar la aplicación en un ambiente real, con configuración por variables de entorno y un endpoint de estado verificable.

Punto de partida

Este práctico continúa el proyecto del TP2 — mismo repositorio, mismos paquetes. Si querés repasar cómo quedó la persistencia antes de sumarle seguridad, mirá la presentación del TP2.

La rama tp3-starter (próximamente en el repo) parte de un TP2 resuelto tal cual quedó — sin ninguna dependencia de seguridad o testing agregada todavía. Agregarlas al pom.xml es la primera consigna del práctico (ver más abajo): a diferencia del TP2, acá la fricción de las dependencias es parte de lo que hay que resolver, no un andamiaje previo.

El dominio del práctico

Sección titulada «El dominio del práctico»

Favoritos y Listas (TP1-TP2) no cambian de forma — siguen siendo lo mismo. Lo que se suma es a quién pertenecen:

  1. Usuario — quien se registra, inicia sesión y es dueño de sus listas. Tiene un rol: USER o ADMIN.
  2. Lista pasa a pertenecer a un Usuario — mismo patrón @ManyToOne que ya usaste entre Favorito y Lista en el TP2, un nivel más abajo en la jerarquía: Usuario → Lista → Favorito.

Un usuario común solo puede ver y modificar sus propias listas (y, por extensión, los favoritos que cuelgan de ellas). Un usuario ADMIN puede ver las listas de cualquiera. El catálogo de productos (/api/productos) sigue público, sin autenticación — es un espejo de solo lectura, no hay nada que proteger ahí.

Forma de trabajo

Sección titulada «Forma de trabajo»

Seguí trabajando sobre el mismo repositorio Maven del TP2. Sumá al README cómo correr los tests, cómo se ejecuta el pipeline de CI, y los pasos para desplegar.

Consignas

Sección titulada «Consignas»

1. Dependencias y configuración

Sección titulada «1. Dependencias y configuración»
  1. Agregá spring-boot-starter-security al pom.xml.
  2. Agregá una librería de JWT (por ejemplo jjwt) para emitir y validar tokens.
  3. Agregá spring-boot-starter-test (ya debería estar) y Testcontainers (testcontainers + testcontainers-junit-jupiter + testcontainers-postgresql) para los tests de integración.
  4. Movė a variables de entorno cualquier dato sensible que hoy esté fijo en application.properties (credenciales de base, el secreto para firmar JWT) — usá ${VARIABLE:valorPorDefecto} para que siga funcionando en local sin configurar nada extra.
  5. Agregá el plugin maven-failsafe-plugin al pom.xml. mvn test (Surefire) solo ejecuta las clases *Test; las pruebas de integración, que por convención terminan en *IT, las ejecuta Failsafe con ./mvnw verify.

2. Usuario: dominio, persistencia y registro

Sección titulada «2. Usuario: dominio, persistencia y registro»
  1. Definí el dominio Usuario (id, email, passwordHash, rol) y su puerto UsuarioRepository, mismo patrón que FavoritoRepository/ListaRepository.
  2. Implementá UsuarioEntity, UsuarioJpaRepository y UsuarioRepositoryAdapter.
  3. Migración V5__create_usuarios.sql (tabla usuarios: id, email único, password_hash, rol).
  4. POST /api/auth/registro: recibe email y contraseña, guarda el usuario con la contraseña hasheada (PasswordEncoder de Spring Security, nunca en texto plano) y rol USER por defecto. Respondé 409 Conflict si el email ya existe.

3. Autenticación: login y JWT

Sección titulada «3. Autenticación: login y JWT»
  1. POST /api/auth/login: recibe email y contraseña, valida contra el hash guardado, y si es correcto devuelve un JWT firmado con el id y el rol del usuario adentro. Si falla, 401 Unauthorized.
  2. Configurá un filtro de Spring Security que lea el header Authorization: Bearer <token>, lo valide, y deje la identidad del usuario disponible para el resto del request.
  3. /api/auth/** y /api/productos/** quedan públicos. Todo lo demás (/api/favoritos/**, /api/listas/**) exige un token válido — sin token o con uno inválido/vencido, 401 Unauthorized.

4. Autorización: propiedad de recursos y rol

Sección titulada «4. Autorización: propiedad de recursos y rol»
  1. Sumá usuarioId al dominio Lista y a ListaEntity (relación @ManyToOne hacia UsuarioEntity, mismo criterio que Favorito → Lista del TP2). Migración V6__add_usuario_id_a_listas.sql.
  2. Al crear una lista, el dueño es el usuario autenticado — nunca un dato que mande el cliente en el body.
  3. En cada operación sobre una lista puntual (GET/DELETE /api/listas/{id}, GET /api/listas/{id}/favoritos, POST /api/listas/{origenId}/mover-favoritos) validá que la lista pertenezca al usuario autenticado, salvo que su rol sea ADMIN. Si no es el dueño ni admin, 403 Forbidden — no 404, para no confundir “no existe” con “no es tuya”.
  4. GET /api/listas devuelve únicamente las listas del usuario autenticado (o todas, si es ADMIN).
  5. Documentá en el README dónde vive esta regla de autorización (¿Service? ¿un filtro? ¿anotaciones?) y por qué la elegiste ahí y no en el Controller.

5. Pruebas

Sección titulada «5. Pruebas»
  1. Unitarias: al menos un test de ListaServiceImpl que confirme que la lista creada queda asociada al usuario autenticado, y uno que confirme que UsuarioServiceImpl nunca guarda una contraseña en texto plano.
  2. De integración, con Testcontainers levantando un PostgreSQL real y Flyway corriendo las migraciones contra esa base limpia en cada ejecución:
    • login con credenciales válidas → 200 con un token;
    • login con credenciales inválidas → 401;
    • acceder a una lista propia → 200;
    • acceder a una lista ajena → 403;
    • acceder a /api/listas sin token → 401;
    • un ADMIN accediendo a una lista ajena → 200.
  3. Nombres: las clases de pruebas unitarias terminan en Test (ListaServiceImplTest) y las de integración en IT (ListaControllerIT), en el mismo paquete que lo que prueban pero bajo src/test/java. Los métodos siguen operación_escenario_resultado, por ejemplo obtener_listaAjena_lanzaAccesoDenegado. El sufijo no es cosmético: decide qué plugin de Maven la ejecuta.

6. Integración continua

Sección titulada «6. Integración continua»
  1. Agregá un workflow de GitHub Actions (.github/workflows/ci.yml) que en cada push compile el proyecto y corra ./mvnw verify: ejecuta las pruebas unitarias (*Test, con Surefire) y las de integración (*IT, con Failsafe), que incluyen las migraciones contra una base limpia (vía Testcontainers) y las pruebas del punto 5.
  2. Confirmá que el workflow falla si rompés un test a propósito, y que vuelve a pasar al arreglarlo.
  3. El workflow corre en un entorno limpio, sin tu PostgreSQL local: toda prueba que levante Spring necesita su propia base, vía Testcontainers. Si el paso de Maven falla con Permission denied, dale permiso de ejecución al wrapper con git update-index --chmod=+x mvnw y subí el cambio.

7. Despliegue

Sección titulada «7. Despliegue»
  1. Desplegá la aplicación en un proveedor gratuito con PostgreSQL (por ejemplo Render), configurando por variables de entorno la conexión a un PostgreSQL remoto y el secreto de JWT.
  2. Confirmá que las migraciones corrieron en esa base remota, que GET /health responde desde la URL pública, y revisá los logs del servicio para confirmar que arrancó sin errores.
  3. No hace falta mantener el servicio activo después de verificarlo — alcanza con la evidencia de que funcionó.

8. Documentación

Sección titulada «8. Documentación»
  1. Actualizá Swagger: los endpoints de /api/auth documentados, y marcá en la descripción de favoritos/listas que ahora requieren autenticación.
  2. Actualizá el README con cómo correr los tests, cómo leer el resultado de CI, y los pasos de despliegue que seguiste.

Evidencia esperada

Sección titulada «Evidencia esperada»
  • Repositorio con el proyecto del TP2 evolucionado, con autenticación y autorización funcionando.
  • Migraciones V5 y V6 sin ediciones posteriores a una ya aplicada.
  • Suite de tests (unitarios + integración con Testcontainers) corriendo en verde localmente y en CI.
  • Link al workflow de GitHub Actions con al menos una corrida exitosa.
  • URL pública del despliegue, con capturas de GET /health y de un endpoint protegido respondiendo 401 sin token y 200 con uno válido.
  • README actualizado con la justificación de dónde vive la lógica de autorización (consigna 4.5).
