Autenticación · teoríaObjetivo 1

¿Quién sos? Dos formas de que la API lo recuerde

Sesión (stateful) El servidor guarda el estado ("este id de sesión es Ana") en memoria o en una base. El cliente solo manda un id de sesión en una cookie. Si el servidor se reinicia o hay varias instancias, hay que compartir ese estado.
Token (stateless) — lo que usamos El servidor no guarda nada. El token (JWT) es la prueba de identidad — autocontenido, firmado, verificable sin ir a ninguna base. Coherente con que toda la API ya es sin estado (REST, visto en Unidad 1).
  • JWT = JSON Web Token: tres partes separadas por puntos — header, payload (claims: quién sos, tu rol, cuándo vence) y firma. La firma es lo que hace que no se pueda inventar o editar un token sin que el servidor lo note.
  • Cómo lo implementamos: el servidor firma el token con un secreto que solo él conoce (app.jwt.secreto). Cualquiera puede leer el contenido de un JWT (no está encriptado, solo firmado) — nunca guardes algo sensible en el payload.
Un JWT, decodificado header: { "alg": "HS384" } payload: { "sub": "1", // id del usuario "rol": "USER", "iat": 1791397821, // emitido "exp": 1791401421 // vence } firma: HMAC-SHA384(header + payload, secreto)
Autenticación · registroObjetivo 1

Nunca la contraseña en texto plano

// UsuarioServiceImpl.registrar
if (repository.existsByEmail(request.email())) {
    throw new EmailDuplicadoException(
        "Ya existe una cuenta con el email " + request.email());
}
Usuario nuevo = new Usuario(
    null, request.email(),
    passwordEncoder.encode(request.password()),  // hash, no texto plano
    Rol.USER);
return aResponse(repository.save(nuevo));
¿Qué es PasswordEncoder? Una interfaz de Spring Security con dos métodos: encode(texto) (hashea) y matches(texto, hash) (compara sin desencriptar — un hash no se puede revertir). Usamos BCryptPasswordEncoder, el estándar de la industria.
  • Cómo lo implementamos: el registro crea siempre un usuario USER — no hay forma de auto-asignarse ADMIN desde la API. Promover a alguien es una operación manual (SQL), a propósito.
  • Si el email ya existe, 409 Conflict — mismo patrón que ListaNoVaciaException del TP2.
Autenticación · login y JWTObjetivo 1

Validar credenciales, emitir el token

// AuthServiceImpl.login
Usuario usuario = usuarioRepository.findByEmail(request.email())
    .orElseThrow(() -> new CredencialesInvalidasException(
        "Email o contraseña incorrectos"));

if (!passwordEncoder.matches(request.password(), usuario.passwordHash())) {
    throw new CredencialesInvalidasException(
        "Email o contraseña incorrectos");
}

String token = jwtService.generarToken(usuario.id(), usuario.rol());
return new LoginResponse(token);
  • Mismo mensaje de error si el email no existe o si la contraseña está mal — distinguirlos le regala información a quien intenta adivinar emails registrados.
  • jwtService.generarToken mete el id y el rol del usuario adentro del token — eso es lo que después va a leer el filtro en cada request, sin volver a consultar la base.
  • CredencialesInvalidasException → 401 (nuevo handler en GlobalExceptionHandler, mismo patrón que siempre).
Autenticación · el filtroObjetivo 1

Un filtro lee el token en cada request

// JwtAuthenticationFilter.doFilterInternal
String header = request.getHeader("Authorization");
if (header != null && header.startsWith("Bearer ")) {
    String token = header.substring("Bearer ".length());
    try {
        Claims claims = jwtService.validarYObtenerClaims(token);
        Long usuarioId = Long.valueOf(claims.getSubject());
        Rol rol = Rol.valueOf(claims.get("rol", String.class));
        var auth = new UsernamePasswordAuthenticationToken(
            usuarioId, null,
            List.of(new SimpleGrantedAuthority("ROLE_" + rol)));
        SecurityContextHolder.getContext().setAuthentication(auth);
    } catch (JwtException e) { /* token inválido: no autentica */ }
}
filterChain.doFilter(request, response);
¿Qué es un filtro? Código que se ejecuta antes de que el request llegue a tu Controller — Spring Security engancha varios filtros en cadena, uno de validación de sesión, uno de CSRF, etc. Este es el único que agregamos nosotros.
  • Cómo lo implementamos: si el token es válido, deja la identidad en el SecurityContext — disponible para todo el resto del request, sin pasarla a mano por cada método.
  • Si no hay token, o es inválido/vencido, simplemente no autentica a nadie — no tira error acá. El error (401) lo decide después Spring Security, según si esa ruta necesitaba autenticación.
Autenticación · qué es públicoObjetivo 1

SecurityConfig: la lista blanca

// SecurityConfig.securityFilterChain
http
  .csrf(csrf -> csrf.disable())
  .sessionManagement(s ->
      s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
  .authorizeHttpRequests(auth -> auth
      .requestMatchers(
          "/api/auth/**", "/api/productos/**",
          "/swagger-ui/**", "/v3/api-docs/**")
      .permitAll()
      .anyRequest().authenticated())
  .addFilterBefore(jwtAuthenticationFilter,
      UsernamePasswordAuthenticationFilter.class);
  • STATELESS: Spring Security no crea ni usa cookies de sesión — coherente con que la identidad vive entera en el JWT de cada request.
  • permitAll() en /api/auth/** (tenés que poder registrarte y loguearte sin estar logueado todavía) y /api/productos/** (catálogo público).
  • anyRequest().authenticated(): todo lo demás — /api/listas, /api/favoritos — exige un JWT válido. Sin token ahí, 401.
  • csrf().disable(): CSRF protege contra ataques que abusan de cookies de sesión del navegador — no aplica a una API stateless sin cookies.
Autorización · teoríaObjetivo 2

"¿Quién sos?" no es lo mismo que "¿podés hacer esto?"

Autenticación (401) "No sé quién sos" — falta el token, o es inválido/venció. Lo resuelve Spring Security solo, antes de llegar a tu código.
Autorización (403) "Sé perfectamente quién sos — y no podés hacer esto." Dos variantes acá: por rol (¿sos ADMIN?) y por propiedad (¿es tuyo este recurso puntual?).
  • La autorización por rol es genérica (cualquier ADMIN puede todo). La autorización por propiedad necesita mirar el dato concreto — no hay forma de saber si la lista 6 es tuya sin consultarla.
  • Por eso no alcanza con Spring Security solo para la propiedad de recursos: esa regla vive en el Service, donde ya tenés la lista cargada.
Autorización · cómo lo implementamosObjetivo 2

buscarPropiaOFallar: el único punto de control

// ListaServiceImpl
private Lista buscarPropiaOFallar(Long id) {
    Lista lista = listaRepository.findById(id)
        .orElseThrow(() -> new RecursoNoEncontradoException(
            "No existe la lista con id " + id));

    boolean esDueno = lista.usuarioId() != null
        && lista.usuarioId().equals(contexto.usuarioActualId());

    if (!esDueno && !contexto.esAdmin()) {
        throw new AccesoDenegadoException(
            "La lista " + id + " no te pertenece");
    }
    return lista;
}
  • Cómo lo implementamos: obtener, eliminar, favoritosDe y moverFavoritos pasan todos por acá — un solo lugar con la regla, igual que buscarOFallar del TP2 centralizaba el 404.
  • ContextoSeguridad es quien sabe leer el SecurityContext — el Service no toca Spring Security directamente, solo le pregunta "¿quién sos?" y "¿sos admin?".
  • 403, no 404, si no es tuya: existe, pero no te la muestro — distinto de "no existe". Mezclar los dos códigos confunde al cliente de la API.
  • crear nunca llama a esto — ahí el dueño se asigna (contexto.usuarioActualId()), no se valida.
Autorización · evidenciaDemostrado

Los tres casos, en vivo

curl GET /api/listas (sin token) HTTP/1.1 401
curl GET /api/listas/6 (token de otro usuario) HTTP/1.1 403 {"detail":"La lista 6 no te pertenece", "status":403,"title":"Forbidden"}
curl GET /api/listas/6 (ADMIN, token propio) HTTP/1.1 200 {"id":6,"nombre":"Mi lista","usuarioId":1}
  • GET /api/listas sin filtro adicional ya devuelve distinto según quién sos: solo tus listas si sos USER, todas si sos ADMIN — mismo endpoint, misma consulta derivada findByUsuarioId, decidido en el Service.
  • Importante: después de promover a alguien a ADMIN en la base (a mano, por SQL), necesita loguearse de nuevo — el rol viaja adentro del JWT viejo, que no se actualiza solo.
Pruebas · teoríaObjetivo 3

Unitarias vs. de integración

Prueba unitaria Prueba una clase aislada — sus dependencias se mockean (Mockito). Rápida, no toca la base ni el contexto de Spring. Sirve para lógica pura: "¿el hash de la contraseña nunca es el texto plano?".
Prueba de integración Levanta la app real (@SpringBootTest) contra una base real — acá es donde entra Testcontainers: un PostgreSQL de verdad, en un contenedor Docker descartable, que se crea y se destruye en cada corrida.
  • ¿Por qué no mockear la base también en los tests de integración? Porque lo que queremos probar es justamente la cadena completa: filtro → Spring Security → Service → JPA → Postgres real con las migraciones de Flyway corridas. Mockear la base ahí sería no probar nada de lo nuevo.
Pruebas · cómo lo implementamosObjetivo 3

Un test de cada tipo

// Unitario — UsuarioServiceImplTest
@Test
void registrar_nuncaGuardaPasswordEnTextoPlano() {
    when(repository.existsByEmail("ana@test.com"))
        .thenReturn(false);
    service.registrar(new RegistroRequest(
        "ana@test.com", "12345678"));

    verify(repository).save(usuarioCaptor.capture());
    assertThat(usuarioCaptor.getValue().passwordHash())
        .isNotEqualTo("12345678");
}

// Integración — ListaControllerIT (Testcontainers)
@Test
void accederAListaAjena_devuelve403() {
    String tokenBob = loguear("bob@test.com");
    mockMvc.perform(get("/api/listas/{id}", listaDeAna)
            .header("Authorization", "Bearer " + tokenBob))
        .andExpect(status().isForbidden());
}
  • Cómo lo implementamos: el test de integración usa @Testcontainers + @Container con PostgreSQLContainer — Flyway corre sus migraciones contra esa base nueva en cada ejecución, igual que contra la real.
  • Mínimo pedido: login válido/inválido (200/401), acceso a lista propia (200), a lista ajena (403), sin token (401), ADMIN accediendo a lista ajena (200).
  • Correlo con ./mvnw verify: ejecuta las unitarias (*Test) y las de integración (*IT, vía Failsafe). Necesita Docker corriendo, igual que para levantar Postgres en desarrollo.

Ahora, en Swagger y la terminal

http://localhost:8080/swagger-ui/index.html
  1. POST /api/auth/registro → crear dos usuarios (vos y un compañero imaginario).
  2. POST /api/auth/login → copiar el token, autorizar en Swagger ("Authorize", pegar Bearer <token>).
  3. POST /api/listas → crear una lista. Mirar que usuarioId coincide con el tuyo, nunca con uno inventado en el body.
  4. Loguearse con el otro token → GET /api/listas/{id} de la primera → 403.
  5. Promover a uno de los dos a ADMIN por SQL, loguearlo de nuevo, repetir el paso anterior → 200.
  6. ./mvnw verify → ver correr la suite completa, con Testcontainers levantando Postgres solo.
